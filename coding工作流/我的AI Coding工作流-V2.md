# 我的 AI Coding 工作流 V2

适用于日常需求、Bug、重构、配置和数据变更。我的默认做法是 **接住现有工单 → 查现场 → 做一个可验收的改动 → 跑证据 → 交给团队现有流程**。任务的后果和不确定性决定每一步做多深。

## 1. 今天接到一张票，直接这样用

打开团队已有的工单和仓库，把下面这段交给公司授权使用的 AI。工单已有上下文时，给链接和本次目标即可。只有工单缺少验收标准，才补一条预期。

~~~text
任务：<工单链接或一句话目标>
验收：<什么情况下，从哪个入口，应该看到什么结果>
边界：<要遵守的业务约定、已有调用方或环境限制，按需填写>

先读项目规则、工作区、相关实现和现有测试，沿真实入口查到受影响的代码或数据。
目标明确且风险低时，直接在授权范围内实现、验证、处理失败并检查 diff。常规需求较大时，先把可验收的第一段和验证办法写在当前任务里，再推进这段。涉及权限、生产数据或难恢复的副作用时，先对齐契约、失败路径和恢复方案，按团队门禁推进。
遇到影响对外行为或数据的未决取舍、超出授权的操作，或者关键验证受阻时，给出具体问题、证据和下一步，继续完成其余能做的工作。
收尾给我：改动与影响、实际跑过的步骤和结果、尚缺的证据、当前可以交到哪一步。
~~~

换项目时，先定位四样东西，再开工。读团队要求的说明，沿本任务相关路径深挖。

| 要定位的东西 | 优先去哪找 |
|---|---|
| 需求、契约和负责人 | 工单、接口或产品文档、模块负责人 |
| 项目约定和运行入口 | README、贡献指南、目录级 Agent 指令、构建脚本 |
| 可用的验证环境和命令 | 既有测试、CI 配置、测试环境说明、可用样例 |
| 数据与交付权限 | 团队 AI 数据规则、审批和发布手册、值班约定 |

每个项目沿用已有的工单、版本管理和评审规范。单次脚本或暂无版本管理的项目，保留一份可比较的改前版本和样例。公司代码、客户数据、内部日志和凭据按其分类与团队规则留在批准的环境，用允许的工具和数据做必要验证。无法向 AI 提供工作材料时，自己做仓库操作，在许可范围内用抽象问题或批准的示例让 AI 辅助。

## 2. 先判断改坏了会怎样

| 档位 | 怎么判断 | 我怎么走 |
|---|---|---|
| **小改** | 行为边界明确，影响局部，容易看到结果和恢复。例如局部文案、文档或有现成复现的低影响修复。 | 一句验收，直接改，跑贴近改动的检查，按团队规则交付。 |
| **常规** | 改用户行为、接口用法或工作链路，需要验证正常与关键失败路径，影响可控。 | 在现有任务补具体验收和兼容要求，按可验收增量实现、自测和审查。 |
| **高风险** | 涉及权限、生产数据、不可逆副作用、重要跨团队契约、关键状态或难以恢复的变更。 | 先对齐契约、影响面、授权和恢复方案。验证关键反例，安排独立复核，走团队批准和发布路径。 |

开工先初判，读到实际调用方或数据写入后再校正。以失败后果为准。一行权限默认值也可能需要高风险路径。产品行为说不清时，先查现行文档、样例和调用方，只把会改变验收或方向的问题交给负责人决策。

## 3. 执行与验证

### 定结果，查现场

1. 找到需求的权威落点。把验收写成「触发条件 → 期望行为 → 可观察结果」，同时写下重要的兼容约束。测试期望取自业务规则、接口契约、负责人确认或可信参考数据。
2. 检查分支、工作区差异和相关测试。已有他人的改动就绕开，确实会互相覆盖时再协调或用隔离工作区。遇到测试红灯，尽量用同环境的改前结果区分历史基线和本次回归。
3. 找实际运行入口、调用方、外部依赖和可复用实现。范围明确就推进。跨端或较大的需求，拆成每段都能从某个入口看见结果的增量，例如先交付一个已有消费者能用的新能力，再迁移其余调用者。

### 做最小的完整改动

1. 用项目现有模式实现。修 Bug 时，尽量先让旧代码在固定输入下暴露问题，再在同一条件下确认修复。能用现成测试、命令或稳定手动步骤复现就复用，值得防的回归再补成自动测试。
2. 每段改完就跑聚焦检查、核对实际 diff 和重要兼容行为。跟踪当前验收、能重跑的证据和下一步。需要并行时才隔离写入，明确各自范围及谁负责集成。
3. 排障尝试迟迟拿不出新证据时，切回诊断。记录期望与实际、环境、最近变更，写下一个假设和能推翻它的观察，再决定下一刀。偶发问题可先用脱敏日志、对照样本或受控插桩获取稳定信号。

### 让验证回答业务问题

| 想证明什么 | 该拿什么证据 |
|---|---|
| 局部规则、文案或配置生效 | 运行针对性的测试、真实命令、文档构建、配置检查或页面操作，观察具体结果。 |
| 一项业务行为成立 | 从正常入口复跑成功场景和最可能出错的场景。按需要核对响应、页面、状态、数据或外部副作用。选最接近实际入口且成本合理的测试层。 |
| 旧行为或历史数据兼容 | 用代表性历史样本、调用方契约或改前快照做对照。明确本次允许发生的差异。 |
| 性能改善 | 先定指标、目标和代表性负载。在可比环境下用相同数据和负载做改前、改后测量，同时检查结果正确性。 |
| 并发、迁移或复杂状态可靠 | 列状态、触发事件及必须始终成立的规则。挑有实际风险的顺序，例如重复、乱序、超时和中途失败，验证业务状态与恢复。迁移追加旧数据、滚动发布兼容性和恢复演练。 |
| Agent 产品的效果改善 | 在固定样例与评分规则下对照基线，包含已知错例，检查实际任务结果与必要的成本或延迟指标。 |

对每条关键验收，记下 **在什么版本和环境、怎么跑、观察到了什么**。修改测试断言、快照或跳过条件时，把理由带进审查。修复审查问题后重跑受影响的验证，最终证据要对应实际交付的 diff 或提交。

### 工作现场的两条分支

- **遗留项目、环境起不来**。先用已有测试环境、固定样例、可重复的手工操作或授权同事代跑获取证据。只有静态检查、模拟依赖或局部验证时，写清覆盖到哪一层。关键行为还缺环境验证，就交付可审草稿，附复现输入、期望、待跑环境和确认人。团队已有放行例外时，由有权的人按原流程处理。
- **线上告警**。优先按值班手册和授权减损，保留时间窗口、版本和可用证据。由真实请求和指标确认缓解，再整理根因、正式修复与回归项。临时缓解和长期修复在事故记录中分别标明。

## 4. 审查、交付和交接

**审查顺序**。先跑项目已有的静态和测试检查，再从工单验收和验证结果看起，沿变更路径看核心逻辑。小改走现有评审即可。常规任务可让同事或另一个获准的会话重点查反例。高风险变更安排独立复核，重点看相邻调用方、权限、数据、失败恢复和回滚。AI 的审查结果可供负责人参考，团队要求的人工批准依原流程办理。

可把这段发给独立审查者：

~~~text
按 <工单/契约和项目规则> 审 <当前 diff/提交>，核对 <已跑检查和结果>。
找一个能让验收失败、破坏已有调用方或造成错误副作用的具体场景。
每条问题写位置、触发条件、用户影响和缺的回归证据。顺带核对测试有没有改弱关键断言。
~~~

**交付摘要**写进团队现有的 PR、MR 或工单。简单改动一两行就够，下面四项按需展开。

~~~text
改动与影响：<解决的行为、受影响的入口或调用者>
已验证：<验收项 → 命令/操作 + 环境 + 关键结果或 CI 链接>
待验证：<具体缺口、在哪个环境验证、谁来确认>
交付状态：<本地已验证 / 待审 / 已合并 / 已发布>，需要时附回退动作和触发条件
~~~

合并和发布使用团队现行权限。高风险上线前确认先后顺序、观测信号和止损动作，尤其检查已有写入能否安全恢复。发布后用对应环境的检查确认结果，CI 和合并记录各自只证明其实际执行的阶段。

**换人或换会话时**，用原工单或 PR 留一条指针。内容包括任务链接、分支/提交及未提交差异、已跑证据、一个下一动作和阻塞。排障中再加上已排除的关键假设及对应证据。接手者以工单、Git 和结果记录核对现场。重复出错的步骤再沉淀到项目已有的测试、脚本或文档里。

## 5. 换个项目也能照着做

| 接到的任务 | 走一遍 |
|---|---|
| CLI 参数报错文案要统一 | **小改。** 运行原命令，核对新文案和原有失败退出码。将命令与结果写进原工单或 PR。 |
| 老系统改订单列表筛选，本地数据库起不来 | **常规。** 从工单确认筛选语义与历史行为。先验证可独立跑的查询逻辑，再用授权测试环境和代表性样本重跑页面筛选。没有环境时把页面验收标为待验证，交付可审草稿和代跑步骤。 |
| 既有接口增加一个可选字段 | **常规。** 先确认调用方和旧客户端契约，挑一个能独立验收的增量。确认旧客户端仍可读、新客户端能读到正确值，并补字段缺省或失败的反例。若涉及未经确认的跨团队契约，升级走高风险路径。 |
| 一行配置默认值会放宽用户权限 | **高风险。** 找授权契约与调用面，确认允许与拒绝的对象。用既有测试或授权环境检查允许、拒绝及缺省情形；让负责人独立复核影响和上线恢复方案。 |

第一张真实小票只用开头提示词和现有项目检查。接下来再试一张常规票。每张票结束花一分钟，记下拿到可信证据花了多久、因为什么返工、换人能否继续。连续出现同一个坑，再把它变成能重跑的检查或一条项目规则。改工作流后用熟悉的任务走一遍，确认 AI 会在授权范围内做到验证与收尾。

页码按压缩包内各 PDF 的物理页序。 [八篇报告原始压缩包](./八篇AI开发报告合集.zip)

| 报告 | 本 SOP 采用的做法 |
|---|---|
| 瓶子 coder · Agent Harness（第 4–6、8–9 页） | 工单和 Git 承载事实，交接留指针。规则只取当前任务所需。精简后用真实任务检查 AI 是否还会继续执行与收尾。 |
| Aurora · 大厂 vibe coding 避坑指南（第 3、7–8 页） | 用触发条件与可观察结果对齐需求，沿调用关系确认范围，用实际 diff 核对；排障靠复现和对照证据。 |
| Thorsten Ball · How I Work with Agents（第 3–7 页） | 按意图、影响面和证据能否被审懂来拆增量。审查时间投入由失败后果决定。 |
| Addy Osmani · Code Review（第 5–10、12–13 页） | 先做机械自检，给 reviewer 固定的改动范围和验收依据；依风险投入人工复核，发布按实际环境信号验收。 |
| Addy Osmani · Verification（第 5–12 页） | 从正常入口检查实际结果。预期来自实现之外的约定。属性测试用于不变量，差分测试用于可信参考对照。 |
| AYi · pstack/TLA+（第 3–7 页） | 状态复杂时先列状态和不变量，用真实代码测关键故障顺序。组合规模值得时再做模型检查，并说明模型假设。 |
| 木子不是木子狸 · HITL Dev Loop（第 2–4、9 页） | 人对目标、关键取舍和交付负责，AI 负责授权范围内的推进和验证。并行、隔离和常驻协作的成本按项目需要衡量。 |
| 黄同学 · AI 开发心得（第 5–8 页） | 简单需求直做，复杂需求切成小增量。验证沿业务实际路径走，人工审查先看验收、再看证据和核心逻辑。 |
