整体架构：两个框架分别负责什么？

用大白话讲：LangChain 帮你把模型、提示词、工具和检索组件接起来；LangGraph 帮你控制这些步骤何时执行、怎样分支、如何恢复。规则明确的流程优先普通 Python 或确定性图，需要模型决策时再使用 Agent。二者不是二选一。

业务需求优先思路
一次分类或信息抽取模型 + 结构化输出
固定问答链和检索LCEL / 普通 Python RAG
模型自行挑选工具create_agent
有分支、并行、暂停、重试的长流程StateGraph
跨部门的长研究任务先确定流程与预算，必要时子图 / 多 Agent

01 / 模型调用与 Messages

P0APIlab_01.py

01 · 这是什么？为什么需要？

ChatModel（聊天模型）是统一的模型接口。Message（消息）不是单纯字符串：角色决定信息来自系统、用户还是模型。把模型想成负责理解问题的同事，应用负责准备上下文和处理结果。

02 · 图解执行过程

03 · 企业场景代码

Python / lab_01.py
from langchain_openai import ChatOpenAI
from langchain_core.messages import SystemMessage, HumanMessage
import os

model = ChatOpenAI(model=os.environ["LLM_MODEL"], temperature=0, timeout=30)
messages = [SystemMessage(content="你是运维助手，只解释现象，不执行操作。"),
            HumanMessage(content="HTTP 502 常见原因是什么？")]
reply = model.invoke(messages)
print(reply.content)
print(reply.usage_metadata)

04 · 代码解析

ChatOpenAI 在初始化时配置模型；invoke 发出一次同步请求；返回 AIMessage，content 是内容，usage_metadata 可能包含 token 统计。temperature=0 不保证完全确定性。

05 · 预期结果（非实测）

输出一段 502 原因说明；usage_metadata 取决于供应商。

06 · 常见坑与边界

不要把 API Key 写进源码；不要把回复对象当字符串拼接。

07 · 动手验收

将用户问题改成 Redis 连接超时，查看回复和 token 字段。

02 / PromptTemplate 与变量填充

P0本地lab_02.py

01 · 这是什么？为什么需要？

Prompt（提示词）可以看成带占位符的模板。固定规则与动态数据分开维护，业务代码只传 service 和 alert，不需要到处拼接字符串。

02 · 图解执行过程

03 · 企业场景代码

Python / lab_02.py
from langchain_core.prompts import ChatPromptTemplate

prompt = ChatPromptTemplate.from_messages([
    ("system", "你是运维助手。仅根据证据回答。"),
    ("human", "服务：{service}；告警：{alert}")
])
messages = prompt.format_messages(service="order-api", alert="CPU 95%")
for message in messages:
    print(message.type, message.content)

04 · 代码解析

from_messages 固定每条消息的角色；花括号是变量名；format_messages 只生成消息，不会访问模型。

05 · 预期结果（非实测）

system 你是运维助手。仅根据证据回答。 human 服务：order-api；告警：CPU 95%

06 · 常见坑与边界

变量名必须一致；模板里的字面 JSON 花括号需要转义为双花括号。用户内容不是可信系统指令。

07 · 动手验收

增加 environment 变量，输出生产环境告警提示词。

03 / LCEL 与 Runnable：链式调用

P0本地lab_03.py

01 · 这是什么？为什么需要？

LCEL（LangChain 表达式语言）用 | 连接 Runnable（可运行组件）。不是异步管道魔法，而是让上一环节的输出成为下一环节的输入。

02 · 图解执行过程

03 · 企业场景代码

Python / lab_03.py
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import RunnableLambda
from langchain_core.messages import AIMessage
from langchain_core.output_parsers import StrOutputParser

prompt = ChatPromptTemplate.from_template("总结告警：{alert}")
# 模拟模型，不花 API 费用
fake_model = RunnableLambda(lambda value: AIMessage(content="排查：" + value.to_string()))
chain = prompt | fake_model | StrOutputParser()
print(chain.invoke({"alert": "CPU 95%"}))

04 · 代码解析

管道输入为字典，prompt 转 PromptValue，模拟模型转 AIMessage，parser 提取文本。真实模型可替换 fake_model。

05 · 预期结果（非实测）

排查：Human: 总结告警：CPU 95%（消息格式可能略有差异）

06 · 常见坑与边界

不要把模型调用结果（已经执行）放在 | 右边；检查每个组件的输入输出类型。

07 · 动手验收

单独打印 prompt.invoke 的类型，再和完整链结果比较。

04 / invoke / batch / ainvoke / stream

P0本地lab_04.py

01 · 这是什么？为什么需要？

同一个 Runnable 可以单次执行、批量执行或异步执行。stream 产出的粒度由组件决定，不必然是 token。

02 · 图解执行过程

03 · 企业场景代码

Python / lab_04.py
import asyncio
from langchain_core.runnables import RunnableLambda

async def enrich(service: str) -> str:
    await asyncio.sleep(0.1)
    return f"{service}: OK"

sync_chain = RunnableLambda(lambda s: s.upper())
print(sync_chain.invoke("api"))
print(sync_chain.batch(["api", "db"], config={"max_concurrency": 2}))

async def main():
    chain = RunnableLambda(enrich)
    print(await chain.ainvoke("api"))
    print(await chain.abatch(["api", "db"]))

asyncio.run(main())

04 · 代码解析

invoke 是同步；batch 保留输入顺序；ainvoke 需要 await；abatch 用于多项并发。真实网络请求必须控制并发和超时。

05 · 预期结果（非实测）

API ['API', 'DB'] api: OK ['api: OK', 'db: OK']

06 · 常见坑与边界

async 函数内调用阻塞式 HTTP SDK 会阻塞事件循环；不要在已运行事件循环里再次 asyncio.run。

07 · 动手验收

让一个服务延迟更久，验证 abatch 的返回顺序。

05 / 结构化输出 Pydantic

P0APIlab_05.py

01 · 这是什么？为什么需要？

让模型输出可校验的对象，而不是让程序从自然语言中猜严重等级。适用于分类、信息抽取和路由。

02 · 图解执行过程

03 · 企业场景代码

Python / lab_05.py
from typing import Literal
from pydantic import BaseModel, Field
from langchain_openai import ChatOpenAI
import os

class Triage(BaseModel):
    service: str
    severity: Literal["low", "high"]
    reason: str = Field(description="简短分类依据")

model = ChatOpenAI(model=os.environ["LLM_MODEL"], timeout=30)
classifier = model.with_structured_output(Triage)
result = classifier.invoke("order-api 错误率 30%，判断等级")
print(result.severity, result.service)
print(result.model_dump())

04 · 代码解析

BaseModel 规定字段和类型；Literal 限制枚举；with_structured_output 由模型集成处理结构化生成与解析。

05 · 预期结果（非实测）

预期为 Triage 对象，severity 可能为 high；不是固定答案。

06 · 常见坑与边界

结构化输出不保证业务事实正确。模型必须支持所选结构化机制；解析失败要显式处理。

07 · 动手验收

加入 confidence 字段并限制 0 到 1，同时增加业务规则复查。

06 / @tool 与参数 Schema

P0本地lab_06.py

01 · 这是什么？为什么需要？

Tool（工具）把 Python 函数包装成模型能够了解名称、描述和参数的能力。直接调用 tool.invoke 可以先测试工具，不依赖模型。

02 · 图解执行过程

03 · 企业场景代码

Python / lab_06.py
from langchain_core.tools import tool

@tool
def get_cpu(service: str) -> dict:
    """查询指定服务的 CPU 使用率，返回百分比（教学模拟）。"""
    data = {"order-api": 95, "payment-api": 40}
    if service not in data:
        return {"error": "unknown service"}
    return {"service": service, "cpu": data[service]}

print(get_cpu.name)
print(get_cpu.args)
print(get_cpu.invoke({"service": "order-api"}))

04 · 代码解析

函数名成为默认工具名；docstring 提供描述；类型注解生成输入 schema；invoke 传字典执行。

05 · 预期结果（非实测）

get_cpu；参数 schema 包含 service；{service: order-api, cpu: 95}

06 · 常见坑与边界

工具输入来自不可信来源，要校验权限、资源归属和参数；示例数据不是监控系统真实查询。

07 / bind_tools 与手动 Tool Calling

P0APIlab_07.py

01 · 这是什么？为什么需要？

Tool Calling（工具调用）中模型只提出工具名和参数，真正执行函数的是应用。手写一轮可以理解框架替你做了什么。

02 · 图解执行过程

03 · 企业场景代码

Python / lab_07.py
import json, os
from langchain_openai import ChatOpenAI
from langchain_core.messages import HumanMessage, ToolMessage
from langchain_core.tools import tool

@tool
def get_cpu(service: str) -> int:
    """查询服务 CPU 百分比（模拟）。"""
    return {"order-api": 95}.get(service, -1)

model = ChatOpenAI(model=os.environ["LLM_MODEL"], timeout=30).bind_tools([get_cpu])
messages = [HumanMessage(content="查询 order-api CPU")]
reply = model.invoke(messages)
messages.append(reply)
for call in reply.tool_calls:
    if call["name"] == get_cpu.name:
        value = get_cpu.invoke(call["args"])
    else:
        value = {"error": "tool not allowed"}
    messages.append(ToolMessage(content=json.dumps(value), tool_call_id=call["id"]))
if reply.tool_calls:
    reply = model.invoke(messages)
print(reply.content, reply.tool_calls)

04 · 代码解析

bind_tools 提供工具定义；遍历 tool_calls；用 tool_call_id 关联一次请求及对应结果；最后再次推理。这里仅演示一轮，下一次可能仍请求工具。

05 · 预期结果（非实测）

若模型发起调用，会拿到模拟 CPU 95，再产生解释或下一次工具请求。

06 · 常见坑与边界

bind_tools 不等于自动执行；不要漏掉并行请求中的任何 ToolMessage；真实循环需设置上限。

07 · 动手验收

打印 reply.tool_calls，观察 name、args、id。

08 / create_agent：完整工具循环

P0APIlab_08.py

01 · 这是什么？为什么需要？

Agent（智能体）是模型在工具反馈基础上决定继续还是结束的循环。LangChain 1.x 的 create_agent 构建在 LangGraph 运行时之上。

02 · 图解执行过程

03 · 企业场景代码

Python / lab_08.py
import os
from langchain.agents import create_agent
from langchain_core.tools import tool
from langchain_openai import ChatOpenAI

@tool
def get_status(service: str) -> str:
    """读取服务状态（模拟），支持 order-api。"""
    return "order-api CPU 95%" if service == "order-api" else "无数据"

agent = create_agent(
    model=ChatOpenAI(model=os.environ["LLM_MODEL"], timeout=30),
    tools=[get_status], system_prompt="先查询证据，再回答，不要编造数据。"
)
result = agent.invoke({"messages": [{"role": "user", "content": "order-api 正常吗？"}]},
                      config={"recursion_limit": 12})
for message in result["messages"]:
    print(message.type, message.content)

04 · 代码解析

create_agent 自动组织模型、工具和循环；输入是 messages state；返回完整状态，通常最后一条是最终模型回复。recursion_limit 限制图步数而非 token。

05 · 预期结果（非实测）

消息序列可能是 human → ai → tool → ai，实际取决于模型。

06 · 常见坑与边界

工具循环不是必然调用工具，也不保证正确；权限限制必须在工具执行端。

07 · 动手验收

新增只读日志工具，观察模型是否选择多个工具。

09 / Middleware：工具错误与调用策略

P1APIlab_09.py

01 · 这是什么？为什么需要？

Middleware（中间件）是在 Agent 固定生命周期中插入逻辑的方式。适合统一错误处理、上下文管理、计数等，而不是把逻辑散落每个工具。

02 · 图解执行过程

03 · 企业场景代码

Python / lab_09.py
import os
from langchain.agents import create_agent
from langchain.agents.middleware import wrap_tool_call
from langchain_core.messages import ToolMessage
from langchain_core.tools import tool
from langchain_openai import ChatOpenAI

@tool
def query_service(service: str) -> str:
    """读取服务状态（教学模拟）。"""
    if service != "order-api":
        raise ValueError("unknown service")
    return "healthy"

@wrap_tool_call
def handle_error(request, handler):
    try:
        return handler(request)
    except ValueError:
        return ToolMessage(content="服务名无效，请核对后重试。",
                           tool_call_id=request.tool_call["id"])

agent = create_agent(ChatOpenAI(model=os.environ["LLM_MODEL"], timeout=30),
                     tools=[query_service], middleware=[handle_error])
print(agent.invoke({"messages": [{"role": "user", "content": "查 xyz 状态"}]},
                   config={"recursion_limit": 8})["messages"][-1].content)

04 · 代码解析

wrapper 包裹工具执行；正常结果原样返回；只捕获预期错误，返回可读反馈供模型纠正。

05 · 预期结果（非实测）

可能返回服务无效说明；调用次数受图步数限制。

06 · 常见坑与边界

不要把所有异常吞掉；同步和异步 middleware 要匹配调用方式；只重试可恢复错误。

07 · 动手验收

增加记录工具名的日志，不记录密钥和敏感参数。

10 / Document / metadata 与文本切块

P0本地lab_10.py

01 · 这是什么？为什么需要？

RAG 不直接把整个文件塞给模型。Document（文档对象）携带正文与 metadata（元数据），切块后依然可以追溯文件名、页码。

02 · 图解执行过程

03 · 企业场景代码

Python / lab_10.py
from langchain_core.documents import Document
from langchain_text_splitters import RecursiveCharacterTextSplitter

pages = [Document(page_content="CPU 高时先查看进程。\n内存高时检查堆使用。\n502 时检查上游服务。",
                  metadata={"source": "runbook.md", "page": 1})]
splitter = RecursiveCharacterTextSplitter(chunk_size=18, chunk_overlap=4,
                                          separators=["\n", "。", ""])
for doc in splitter.split_documents(pages):
    print(repr(doc.page_content), doc.metadata)

04 · 代码解析

length 默认按字符计算；overlap 是切块重叠目标，并非每两块精确重复固定长度；元数据随切块保留。

打印多个片段及相同 source、page。

真实 PDF 页码由解析器决定，可能从 0 开始；不要把字符长度当 token 数。

07 · 动手验收

将 chunk_size 改为 35，比较块数量和语义完整性。

11 / Embedding、向量库与 Retriever

P0本地lab_11.py

01 · 这是什么？为什么需要？

Embedding（向量化）把文本转成数字向量；向量库按相似度找到候选文档；Retriever（检索器）把检索过程封装为统一接口。下面使用教学词项向量，不是真实语义模型。

02 · 图解执行过程

03 · 企业场景代码

Python / lab_11.py
from langchain_core.embeddings import Embeddings
from langchain_core.vectorstores import InMemoryVectorStore
from langchain_core.documents import Document

class DemoEmbeddings(Embeddings):
    words = ["CPU", "内存", "502"]
    def embed_query(self, text):
        return [float(text.count(word)) for word in self.words]
    def embed_documents(self, texts):
        return [self.embed_query(text) for text in texts]

store = InMemoryVectorStore(DemoEmbeddings())
store.add_documents([
    Document(page_content="CPU CPU 高：检查进程", metadata={"source": "cpu.md"}),
    Document(page_content="内存不足：检查堆", metadata={"source": "memory.md"}),
    Document(page_content="502：检查上游", metadata={"source": "http.md"})])
retriever = store.as_retriever(search_kwargs={"k": 1})
for doc in retriever.invoke("CPU 高怎么办？"):
    print(doc.page_content, doc.metadata)

04 · 代码解析

自定义 Embeddings 接口提供 query 和 documents 两种向量化方法；InMemoryVectorStore 进行本地检索；k 控制返回候选数。

05 · 预期结果（非实测）

01 · 这是什么？为什么需要？

from typing import TypedDict, Literal
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    cpu: int
    result: str

def classify(state: State):
    return {}
def route(state: State) -> Literal["high", "low"]:
    return "high" if state["cpu"] >= 90 else "low"
def investigate(state: State):
    return {"result": "进入排查"}
def close(state: State):
    return {"result": "无需升级"}

b = StateGraph(State)
for name, fn in [("classify", classify), ("investigate", investigate), ("close", close)]:
    b.add_node(name, fn)
b.add_edge(START, "classify")
b.add_conditional_edges("classify", route, {"high": "investigate", "low": "close"})
b.add_edge("investigate", END)
b.add_edge("close", END)
g = b.compile()
print(g.invoke({"cpu": 95}))
print(g.invoke({"cpu": 40}))

class State(TypedDict):

    result: str

def review(state: State):

01 · 这是什么？为什么需要？

Retry（重试）解决临时故障，不是让所有业务错误无限重复。图可对节点设置重试策略，网络请求仍需自己的超时。

02 · 图解执行过程

Python / lab_22.py
from typing import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.types import RetryPolicy

class State(TypedDict):
    status: str
attempts = 0  # 仅教学故障注入，生产不要用全局计数共享请求

def fetch(state: State):
    global attempts
    attempts += 1
    if attempts == 1:
        raise TimeoutError("simulated transient failure")
    return {"status": "ok"}

b = StateGraph(State)
b.add_node("fetch", fetch, retry_policy=RetryPolicy(max_attempts=2,
    initial_interval=0.1, jitter=False, retry_on=TimeoutError))
b.add_edge(START, "fetch")
b.add_edge("fetch", END)
print(b.compile().invoke({}))
print("attempts:", attempts)

04 · 代码解析

retry_on 指定可恢复异常；max_attempts 包含初次尝试；失败超过上限会抛出错误。

05 · 预期结果（非实测）

06 · 常见坑与边界

不要重试参数错误或未授权调用；重试有副作用的 API 要使用后端原子幂等键；checkpoint 不保证 exactly-once。

25 / 异步节点与并发 I/O

P0本地lab_25.py

01 · 这是什么？为什么需要？

LLM、搜索与指标查询通常是 I/O 密集型任务。asyncio.gather 可以在节点内部并发等待独立操作；图级并行是另一层编排。

02 · 图解执行过程

03 · 企业场景代码

Python / lab_25.py
import asyncio
from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    evidence: list[str]
async def cpu():
    await asyncio.sleep(0.1)
    return "CPU 95%"
async def logs():
    await asyncio.sleep(0.2)
    return "upstream timeout"
async def collect(state: State):
    data = await asyncio.wait_for(asyncio.gather(cpu(), logs()), timeout=1)
    return {"evidence": data}

b = StateGraph(State)
b.add_node("collect", collect)
b.add_edge(START, "collect")
b.add_edge("collect", END)
g = b.compile()

async def main():
    print(await g.ainvoke({}))
asyncio.run(main())

04 · 代码解析

两个协程几乎同时等待；gather 输出顺序对应输入顺序；wait_for 为整个收集设置超时；异步图用 ainvoke。

05 · 预期结果（非实测）

{evidence: [CPU 95%, upstream timeout]}。理论等待约 0.2s，不含开销。

06 · 常见坑与边界

阻塞 SDK 要替换为异步客户端或合理使用 to_thread；gather 首个异常并不自动取消所有其他任务。

27 / FastAPI + astream + SSE

P0本地服务lab_27.py

01 · 这是什么？为什么需要？

SSE（服务器发送事件）把后端生成的事件逐条推给浏览器。LangGraph 管任务状态与事件生成，FastAPI 管 HTTP 请求和传输。

02 · 图解执行过程

03 · 企业场景代码

Python / lab_27.py
import json, asyncio
from typing import TypedDict
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
from pydantic import BaseModel
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    service: str
    result: str
async def diagnose(s: State):
    await asyncio.sleep(0.2)
    return {"result": s["service"] + ": simulated CPU high"}
b = StateGraph(State)
b.add_node("diagnose", diagnose)
b.add_edge(START, "diagnose")
b.add_edge("diagnose", END)
graph = b.compile()
app = FastAPI()
class Request(BaseModel):
    service: str

@app.post("/diagnose/stream")
async def stream(req: Request):
    async def events():
        try:
            async for update in graph.astream({"service": req.service}, stream_mode="updates"):
                yield "data: " + json.dumps(update, ensure_ascii=False) + "\n\n"
            yield "event: done\ndata: {}\n\n"
        except Exception:
            yield 'event: error\ndata: {"message":"diagnosis failed"}\n\n'
    return StreamingResponse(events(), media_type="text/event-stream")

04 · 代码解析

用 uvicorn 运行该文件对应模块；POST 请求用 curl -N 或前端 fetch 读取流；浏览器原生 EventSource 通常只支持 GET。HTTP 响应开始后不能再更改状态码。

05 · 预期结果（非实测）

data: {"diagnose": {"result": "order-api: simulated CPU high"}}，然后 done 事件。

06 · 常见坑与边界

生产需要断连处理、认证、代理缓冲配置、心跳、任务取消或后台任务语义、异常日志。SSE 不是持久化消息队列。

07 · 动手验收

增加 /health；在节点内部用 custom writer 推送阶段进度。

29 / OnCall：智能运维诊断工作流

P0本地lab_29.py

01 · 这是什么？为什么需要？

把前面的零散知识串成企业常见流程：Java 业务控制面提交告警，Python 图负责采集、分析、给出建议。这里不执行真实生产操作。

02 · 图解执行过程

03 · 企业场景代码

Python / lab_29.py
import operator
from typing import TypedDict, Annotated, Literal
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import interrupt, Command

class Incident(TypedDict):
    incident_id: str
    service: str
    cpu: int
    evidence: Annotated[list[str], operator.add]
    proposal: str
    decision: str

def classify(s: Incident):
    return {}
def route(s: Incident) -> Literal["high", "low"]:
    return "high" if s["cpu"] >= 90 else "low"
def fanout(s: Incident):
    return {}
def metrics(s: Incident):
    return {"evidence": [f"CPU {s['cpu']}%"]}
def logs(s: Incident):
    return {"evidence": ["模拟日志：upstream timeout"]}
def summarize(s: Incident):
    return {"proposal": "证据：" + "；".join(sorted(s["evidence"])) + "。建议人工检查上游。"}
def review(s: Incident):
    approved = interrupt({"incident_id": s["incident_id"], "proposal": s["proposal"]})
    return {"decision": "approved_for_manual_review" if approved is True else "rejected"}
def close(s: Incident):
    return {"decision": "monitor_only"}

b = StateGraph(Incident)
for name, fn in [("classify", classify), ("fanout", fanout), ("metrics", metrics),
                 ("logs", logs), ("summarize", summarize), ("review", review), ("close", close)]:
    b.add_node(name, fn)
b.add_edge(START, "classify")
b.add_conditional_edges("classify", route, {"high": "fanout", "low": "close"})
b.add_edge("fanout", "metrics")
b.add_edge("fanout", "logs")
b.add_edge(["metrics", "logs"], "summarize")
b.add_edge("summarize", "review")
b.add_edge("review", END)
b.add_edge("close", END)
graph = b.compile(checkpointer=InMemorySaver())

def run_demo():
    cfg = {"configurable": {"thread_id": "inc-001"}}
    initial = {"incident_id": "inc-001", "service": "order-api", "cpu": 95, "evidence": []}
    paused = graph.invoke(initial, cfg)
    assert "__interrupt__" in paused
    print(paused["proposal"])
    final = graph.invoke(Command(resume=True), cfg)
    assert final["decision"] == "approved_for_manual_review"
    print(final["decision"])
    low = graph.invoke({**initial, "incident_id": "inc-002", "cpu": 30},
                       {"configurable": {"thread_id": "inc-002"}})
    assert low["decision"] == "monitor_only"
    print(low["decision"])

if __name__ == "__main__":
    run_demo()

04 · 代码解析

classify 和 fanout 只负责分支及调度；metrics/logs 是独立并行节点；Reducer 把证据合并，summarize 构造建议，review 暂停等待。Java 端在真实项目中负责告警、审批权限、审计与受控执行，Python 不绕过业务系统。

05 · 预期结果（非实测）

证据包含 CPU 95% 和模拟日志；批准分支输出 approved_for_manual_review；低风险输出 monitor_only。

06 · 常见坑与边界

示例没有真正接 Prometheus、ELK、数据库或 LLM；不能直接上线。审批只确认建议，不代表命令已执行；新任务需要唯一 thread_id。

07 · 动手验收

依次完成：增加 Redis 指标、用真实 HTTP 客户端替换模拟数据、给建议生成节点接入结构化模型输出、接 FastAPI 并为拒绝和超时写测试。

30 / DeepResearch：有界搜索与评审循环

P0本地lab_30.py

01 · 这是什么？为什么需要？

研究任务常常需要多轮搜索、证据检查和迭代。核心不是让模型永远自主探索，而是明确终止条件与预算。

02 · 图解执行过程

03 · 企业场景代码

Python / lab_30.py
from typing import TypedDict, Annotated, Literal
import operator
from langgraph.graph import StateGraph, START, END

class Research(TypedDict):
    question: str
    rounds: int
    evidence: Annotated[list[str], operator.add]
    report: str

def plan(s: Research):
    return {"rounds": 0}
def search(s: Research):
    round_no = s["rounds"] + 1
    # 教学模拟；真实实现需要检索来源、去重和来源可靠性核验
    evidence = ["模拟来源：监控数据"] if round_no == 1 else ["模拟来源：发布记录"]
    return {"rounds": round_no, "evidence": evidence}
def review(s: Research):
    return {}
def next_step(s: Research) -> Literal["again", "done"]:
    enough = len(set(s["evidence"])) >= 2
    return "done" if enough or s["rounds"] >= 3 else "again"
def report(s: Research):
    status = "证据达到演示阈值" if len(set(s["evidence"])) >= 2 else "证据不足"
    return {"report": status + "：" + "；".join(s["evidence"])}

b = StateGraph(Research)
for name, fn in [("plan", plan), ("search", search), ("review", review), ("report", report)]:
    b.add_node(name, fn)
b.add_edge(START, "plan")
b.add_edge("plan", "search")
b.add_edge("search", "review")
b.add_conditional_edges("review", next_step, {"again": "search", "done": "report"})
b.add_edge("report", END)
g = b.compile()
r = g.invoke({"question": "订单服务异常原因", "evidence": []}, config={"recursion_limit": 20})
assert r["rounds"] == 2
print(r["report"])

04 · 代码解析

rounds 是业务预算，recursion_limit 是框架保护上限；两者要区分。evidence reducer 保存每轮新增证据，review 只做下一轮决策，报告明确是否达到阈值。

05 · 预期结果（非实测）

证据达到演示阈值：模拟来源：监控数据；模拟来源：发布记录。

06 · 常见坑与边界

证据条数不等于可信度；真实评审应检查来源、覆盖范围、矛盾和引用。搜索结果中可能存在提示注入。

07 · 动手验收

让 search 每次返回相同来源，验证第三轮退出并标记证据不足；随后加入 Send 并行子查询。
